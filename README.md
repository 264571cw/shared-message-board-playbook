## 0. 先说结论

当你同时用几个 AI 工具干活（一个负责裁决与派单、一个负责执行、一个负责环境与门禁、再加一个人类拍板），**最大的损耗不是模型不够强，而是信息在工具之间断掉**。

把工具合并成一个不是解法——它们各有各的长处和权限边界。成本低得多的做法是：给它们**一块共享信箱 + 一条主从规则**。我们这么干了几个月，下面是能直接照抄的部分，以及我们踩过的坑。

## 1. 你大概率遇到过这些症状

- 同一个任务在两个工具里各开一次工，产出还不太一样
- A 说「改完了」，B 不知道，于是 B 又改了一遍
- 板上公告说「这单作废」，可文件里明明是「已完工交付」
- 引用一张件时拿错——因为存在两张同号件
- 某个端报「我查过了，没有新任务」，其实它查错了信箱名

这些都不是模型能力问题，是**协作协议缺失**。

## 2. 架构：五件东西

1. **一块板**：一个极简 HTTP 收件箱。只需要两个动作——「追加一条」和「按水位取新的」。每条带：自增 id、时间戳、发件端、收件端（或广播）、类型、正文。
2. **端名与令牌台账**：每个参与方一个端名 + 一把令牌；台账写明谁归属哪块板、能读写什么。**收件名 = 台账上的端名**，不允许写别名。
3. **三拍循环**：每个端开工先「拉信 → 处理 → 回帖」。不回帖等于没做。
4. **文件为总线，消息为中断**：结论、证据、状态写进文件；板上的帖子只负责「通知有人该去看文件了」。即时消息**不得**当作完成信号。
5. **一条硬规则**：**文件层是事实源，板帖只是通知。** 两者冲突时以文件为准。

## 3. 五条设计取舍（以及各自代价）

**（1）单写者。** 同一份资产同一时刻只有一个端能写，其他端只能提请求。
代价：要排队。收益：不会互相覆盖，出问题能追到唯一一次写入。

**（2）水位用 id + 时间戳双比对。** 只记 id 的话，板一旦归档重排 id，你会静默跳消息或重复处理。
代价：多一点状态。收益：不丢不重。

**（3）收件名精确匹配，大小写敏感。** 这不是缺陷，是「显式身份」的代价。我们为此吃过一次大的：用新端名写的定向件 84 条，旧写法只匹配到 3 条——**查询返回 200、零警告、还打了勾说「没有新任务」**。
教训一句话：**返回 0 不等于没有问题，也可能只是查错了地方。**

**（4）双板 + 只读联邦。** 内外网各一块板，单向同步。
代价：有滞后，且必须先想清「哪块是权威板」。收益：内网资产不外露。

**（5）必须停机才能改的配置，提前发维护窗口通告。** 代价：多一道手续。收益：不会有人在那 12 秒里发帖丢件。有补投队列更好，没有就至少要有通告。

## 4. 最小可复制路径（不绑定任何厂商）

**服务端**：任何能存「一行一条 JSON」的 HTTP 服务就够。两个接口——追加、按水位取新的——加一个自定义鉴权头。
**不要**拿云笔记、聊天软件当板：它们没有稳定的自增 id 和水位语义，你会先丢消息，再花一周查「为什么偶尔少一条」。

**客户端**：任何能跑脚本的 AI 工具都行，伪代码 30 行：

```
水位 = 读本地 state
新件 = GET /messages?since=水位
for 件 in 新件:
    if 件.收件端 in (我, all):
        处理(件); 回帖(件.id)
水位 = max(件.id); 写本地 state
```

**与具体工具的集成只有两层**：工具化（把拉信/发帖做成原生工具，模型直接调）或脚本化（让模型跑一段脚本）。前者体验好，后者零依赖。


## 5. 我们踩过的七个坑（按杀伤力排序）

1. **端名大小写／别名不一致 → 静默漏件。** 症状：返回 0 条或只有旧件，且没有任何报错。
   我们在一周内踩了三次：旧显示名 → 漏 84 条；规范小写 → 只拿到 3 条大写的；**把收件方写成大写开头 → 对方按小写拉，一条都看不到**。三次发件方看到的都是「发送成功」。
2. **归档重排 → id 水位失效。** 症状：消息「跳号」，或同一条被处理两次。
3. **把板帖当事实源 → 误发「作废／停手」令。** 症状：给一份已经合格的交付物打上作废标记。
   判据：**收到任何停手令，先核文件层（状态文件 + 完工回件）再动手。**
4. **停机改配置 → 上板帖丢。** 症状：作业端以为发成功了，板上没有。
5. **一个名字两个工位 → 身份歧义。** 症状：读帖方无法判断「这话它有没有资格说」。
   判据：**身份要显式，别靠推断。**
6. **令牌复制成多个副本 → 泄露面。** 症状：备份文件里还留着旧令牌。
   判据：改完配置先扫一遍明文令牌，再决定能不能把目录交出去。
7. **「条数守恒」假绿。** 症状：改完文件行数、字数都对，但行尾（CRLF↔LF）或 BOM 全变了。
   判据：**改动前后按字节比五元组——CRLF 数／裸 LF 数／裸 CR 数／BOM／总字节。** 条数守恒不是格式守恒。

## 6. 这套东西有没有用：五个自检问题

能一句话答上四个以上，说明你的协作是「可追溯」的；答不上，说明你其实在靠记忆协作：

1. 这条结论出自哪台机器、哪个端？
2. 它对应的文件在哪、什么时候写的？
3. 谁授权改的这一步？
4. 改完之后，有没有第三方独立核验？
5. 如果现在有人说「这单作废」，你能在 1 分钟内查到它到底作废了没有？

## 7. 先说清楚不适合什么

- 它不是消息队列：不保证投递语义与顺序
- 不做实时协作：轮询间隔决定延迟
- **不要把裸露的板放到公网**：板上任何能发帖的人，都能让「收到消息就自动处理」的端去干活——这是提示注入面
- 只有两个端时，别上双板联邦，成本不划算
